# Testing Patterns

**Analysis Date:** 2026-08-15
**Scope:** Full Repository

This document details the testing architecture, frameworks, and mocking patterns used across the UIMS monorepo.

## Test Framework

- **Runner & Assertion**: **Vitest** is used universally across both the API and Web applications, providing a compatible API with Jest (`describe`, `it`, `expect`).
- **Environments**: 
  - API uses the standard Node environment (`environment: 'node'`).
  - Web uses Happy DOM (`environment: 'happy-dom'`).
- **End-to-End (E2E)**: **Playwright** is configured at the workspace level, though specific test implementations are not currently active in the apps.

## Test File Organization

Tests are strictly co-located with their implementation files.

- **API**: Uses the `.spec.ts` suffix (e.g., `users.service.spec.ts`).
- **Web**: Uses the `.test.ts` suffix for stores and services (e.g., `auth.store.test.ts`).

## Test Structure

Standard BDD structural patterns are used. Globals are enabled in `vitest.config.ts`, so explicit imports for `describe`, `it`, and `expect` are not strictly required, though they are often imported explicitly from `'vitest'` for clarity.

```typescript
import { describe, expect, it } from 'vitest';

describe('ModuleName', () => {
  it('should exhibit specific behavior', () => {
    // Arrange
    // Act
    // Assert
  });
});
```

## Mocking

- **Function Mocking**: Uses Vitest's `vi.fn()` for creating spy functions.
- **Dependency Injection (API)**: When mocking NestJS services or database adapters (like Prisma), literal objects are provided with `vi.fn()` properties and type-casted via `as unknown as Type`. This avoids heavy mocking libraries and keeps tests fast.

```typescript
// Example from apps/api/src/modules/auth/auth.service.spec.ts
let mockUsersService = {
  findByEmail: vi.fn(),
};

service = new AuthService(
  mockUsersService as unknown as UsersService,
  mockJwtService as unknown as JwtService,
);

// Usage
mockUsersService.findByEmail.mockResolvedValue({ id: '1', email: 'test@test.com' });
```

- **State Store Mocking (Web)**: Zustand stores are typically tested by directly interacting with the store state, utilizing `beforeEach` to reset state (e.g., `useAuthStore.setState({ user: null, token: null })`).

## Coverage

Test coverage collection is not explicitly configured or mandated in the default Vitest configs (`vitest.config.mts` / `vitest.config.ts`), though `passWithNoTests: true` is enabled to allow clean CI runs even if test suites are empty.

## Test Types

- **Unit Tests**: The predominant test type implemented. Focuses on testing individual NestJS services, controllers, and React state stores (Zustand). Component testing (React) is currently minimal/absent.
- **E2E Tests**: Scaffolding exists via package.json scripts (`test:e2e`), but no suites are currently active.
